# P5.8 — Device Passport Trust Anchor Abstraction Report

## Executive Summary

Phase **P5.8 Device Passport Trust Anchor Abstraction** establishes a storage- and backend-agnostic Trust Anchor layer on top of the verified Device Passport (P5.6/P5.7). It introduces a domain representation for immutable passport fingerprints (`TrustAnchor`), a storage interface (`TrustAnchorRepository`), an in-memory reference implementation (`InMemoryTrustAnchorRepository`), an orchestration service (`DevicePassportTrustService`), and corresponding REST API endpoints (`POST /devices/{id}/passport/anchor`, `GET /devices/{id}/passport/anchor`, `GET /devices/{id}/passport/anchor/verify`).

P5.8 completely isolates domain logic from distributed ledger technologies, preparing the exact boundary for a future **Phase P5.9 Hyperledger Fabric adapter**.

## 1. Architectural Design

```text
       DeviceRecord + Event History + DevicePassport
                            ↓
             Passport Verification (P5.7)
          [VERIFIED | WARNING | INVALID]
                            ↓
         DevicePassportTrustService (P5.8)
       [STRICT Policy: only VERIFIED allowed]
                            ↓
            Deterministic Trust Payload
            canonicalize_trust_payload(...)
                            ↓
            TrustAnchorRepository (Protocol)
               ├── InMemoryTrustAnchorRepository (P5.8)
               └── HyperledgerFabricTrustAnchor (P5.9 future)
```

### Core Components
1. **Domain Model (`TrustAnchor`)**:
   - `anchor_id`: Unique identifier for the trust anchor (`anc-<12-hex>`).
   - `device_id`: Canonical public device identifier.
   - `passport_fingerprint`: Cryptographic SHA-256 fingerprint generated by P5.7.
   - `algorithm`: Default `"sha256"`.
   - `anchored_at`: ISO-8601 UTC timestamp of anchoring.
   - `status`: `TrustAnchorStatus.ANCHORED`.
   - `metadata`: Flexible context mapping (e.g. environment, submitter, or block height in future adapters).

2. **Repository Protocol & Reference Implementation**:
   - `TrustAnchorRepository`: Defines `save()`, `get_by_device_id()`, `exists()`, `count()`, and `clear()`.
   - `InMemoryTrustAnchorRepository`:
     - **Idempotency**: Anchoring the exact same passport fingerprint returns the existing `TrustAnchor` without duplication.
     - **Conflict Rejection**: Attempting to anchor a different fingerprint onto an already anchored device raises `AnchorConflictError` (HTTP 409 Conflict), preventing silent data overwrites.

3. **Trust Orchestration Service (`DevicePassportTrustService`)**:
   - Executes P5.7 verification prior to anchoring.
   - **Policy Enforcement**:
     - `STRICT`: Only `VERIFIED` passports can be anchored. Passports with `WARNING` or `INVALID` are rejected (`PassportNotAnchorableError`).
     - `PERMISSIVE`: Passports with `VERIFIED` or `WARNING` can be anchored; `INVALID` is always rejected.
   - **Anchor Verification**: Re-evaluates current passport fingerprint against anchored record and returns `VERIFIED`, `MISMATCH`, or `NOT_FOUND`.

4. **Strict Read/Write Boundaries**:
   - `POST /devices/{id}/passport/anchor`: Write permitted **only** to the Trust Anchor repository.
   - `GET /devices/{id}/passport/anchor`: Read-only.
   - `GET /devices/{id}/passport/anchor/verify`: Strictly read-only; **zero** mutations to `DeviceRecord`, **zero** mutations to `DevicePassport`, **zero** audit events emitted, and **zero** modifications to stored anchors.

## 2. API Endpoints

| Method | Route | Status Codes | Description |
|---|---|---|---|
| `POST` | `/devices/{device_id}/passport/anchor` | `201 Created` (new)<br>`200 OK` (idempotent)<br>`400 Bad Request` (invalid passport)<br>`404 Not Found` (device missing)<br>`409 Conflict` (fingerprint conflict) | Verifies passport integrity and anchors fingerprint. |
| `GET` | `/devices/{device_id}/passport/anchor` | `200 OK`<br>`404 Not Found` | Retrieves existing trust anchor. |
| `GET` | `/devices/{device_id}/passport/anchor/verify` | `200 OK`<br>`404 Not Found` (device missing) | Recomputes passport fingerprint and compares with stored anchor (`VERIFIED`, `MISMATCH`, `NOT_FOUND`). |

## 5. Known Limitations & P5.9 Recommendations

1. **In-Memory Volatility**: The reference `InMemoryTrustAnchorRepository` holds records in process memory for unit testing and local development.
2. **P5.9 Recommendation**: Create a `HyperledgerFabricTrustAnchorRepository` implementing `TrustAnchorRepository` that commits the canonical `(device_id, passport_fingerprint, timestamp)` payload to Hyperledger Fabric channel smart contracts via peer endorsements.
